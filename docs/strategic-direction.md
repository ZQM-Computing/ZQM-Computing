# ZQM Computing — Strategic Direction

**Status:** Public-facing strategy summary. This document describes direction, not a claim that every listed capability is already complete.

## Mission

Publish practical, reproducible geospatial engineering patterns that help developers and data practitioners build reliable spatial systems. ZQM Computing is a professional technical portfolio and open-source contribution program.

## Strategic priorities

1. **Engineering credibility:** make examples reproducible, dependencies explicit, expected outputs clear, and limitations honest.
2. **Portfolio coherence:** use the geospatial-patterns index as the entry point; keep repository purpose, license, status, quick start, and contribution guidance consistent.
3. **Developer usefulness:** prioritize working examples, testable patterns, clean documentation, and actionable issue/PR review over repository count or vanity metrics.
4. **Maintainability and security:** keep dependencies, workflows, secret handling, licenses, and repository ownership understandable; use CI where it adds durable value.
5. **Selective connection to ZQM Labs:** demonstrate real-world application through location-based games when relevant, without merging the brands or exposing internal research systems.

## What success looks like

- A new user can identify the right repository and run a supported example.
- Public code has a clear license, prerequisites, expected result, known limitations, and maintenance status.
- Changes are reviewable and validated; claims about testing match actual evidence.
- The portfolio is useful to geospatial developers, analysts, and data engineers.
- Shared capabilities support ZQM Labs only when doing so does not compromise privacy, security, or ZQM Computing's technical focus.

## Scope boundaries

- Keep Project Volusia research/data systems internal and access-controlled.
- Do not use ZQM Computing as a channel for flood-modeling or resilience-data sharing.
- Do not reference Clearview on ZQM GitHub.
- Do not expand the name “ZQM Computing.”
- Preserve the visual identity rule that Dr. Z appears in every ZQM logo. The lantern motif is reserved for Halloween use and should not become a general ZQM Computing symbol.

## Operating principles

- Prefer a tested, maintainable example over an unverified feature.
- Identify canonical repositories and avoid unexplained duplicated sources.
- Treat CI success as evidence only for the checks that actually ran.
- Review security, licensing, and data exposure before publishing.
- Establish baseline metrics before setting numeric targets.

## Roadmap

**Stabilize:** establish repository health baselines; repair broken quick starts, links, licenses, and inaccurate setup instructions.

**Standardize:** apply a consistent README/release convention, improve the umbrella index, and define ownership and support expectations.

**Demonstrate:** publish selected end-to-end examples that show how components fit together, with reproducible data and clearly documented limitations.

**Sustain:** review maintenance cost and adoption evidence quarterly; archive or consolidate only through an explicit, reviewed decision.

## Measures

Track reproducible quick starts, selected clean-environment test results, broken-link counts, stale documentation, critical issue resolution, and reuse signals where available. Do not set targets until a reliable baseline exists.

## Relationship to ZQM Labs

ZQM Computing and ZQM Labs remain distinct brands. ZQM Computing focuses on geospatial engineering; ZQM Labs focuses on global, community-centered games. Public cross-links should help readers, while internal Project Volusia services and data remain private.

The detailed joint roadmap and operational controls are maintained in the private ZQM Labs engineering workspace.
